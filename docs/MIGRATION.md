# 从旧插件迁移到 dshm-boot-rescue v1.1.0

> 状态：**迁移文档（离线源码候选 r2 阶段）**。本轮没有发布、没有可安装发布包、没有真机执行。
> 真实安装/救援/恢复与首次真实配置写入必须等待后续单独授权。本文步骤供用户后续手动执行参考。

## 0. 原则

- 最终运行状态**只保留一个**合并版插件：`dshm-boot-rescue@1.1.0`。
- 合并版**不自动停用/卸载**旧 `dshm-backup` 插件，也不删除插件包/数据/工作区。
- 旧备份插件仍在安装时：合并版备份写入进入**共存只读**；救援功能仍可用。
- **同核心版本是硬门槛**：备份核心版本/格式与当前不一致或未知时，恢复被直接拒绝；没有跨版本确认旁路。
- 安装标识必须使用用户手动发布后的**固定版本标签**；不要把浮动 `#main` 当作安全插件长期安装依据。
- 每次真实写入前都必须有快照、校验、预览与用户确认。

## 1. 迁移顺序

1. **手动备份并校验**
   - 用现有 `dshm-backup@0.1.8` 做一次手动备份；
   - 在旧备份面板执行“校验备份”，确认 SHA-256 通过；
   - 记录备份文件名与 SHA-256（备份含明文聊天/工作区，请勿上传或外发）。
2. **安装合并版（固定标签，用户手动操作）**
   - 安装 `dshm-boot-rescue@1.1.0`（发布后使用固定 tag/包，不使用浮动分支）；
   - 安装后**必须冷重启**：划掉后台，重新打开应用（页面刷新无效）。
3. **冷重启后验证**
   - 打开“安全中心”面板，确认：
     - 救援自检/诊断正常（`/health`、`/state` 可读）；
     - 备份列表能只读看到旧插件既有备份（标注“旧插件既有备份（只读发现）”）；
     - 若旧插件仍安装并启用，界面显示“共存只读模式”，所有备份写入按钮禁用并显示原因。
4. **用户手动移除旧备份插件**
   - 由用户在插件管理中手动移除 `dshm-backup`（合并版不会自动停用/卸载）；
   - 再次**冷重启**。
5. **冷重启后重新评估**
   - 打开“安全中心 → 备份/恢复”，确认共存只读提示消失、写入按钮可用；
   - 建议先做一次手动备份并校验，再执行任何恢复操作。
6. **最终状态**
   - 只保留 `dshm-boot-rescue@1.1.0` 一个插件入口与一个面板；
   - 不要求两个插件长期并存。

## 2. 旧备份与数据目录

| 目录 | 处理 |
|---|---|
| `<可见下载目录>/dshm-backup/backups/` | **只读发现**：列表/校验/预览可用；共存期间不写入、不轮换、不迁移 |
| `$DSH_HOME/dshm-backup/`（旧状态/锁/日志） | **不读写覆盖**；合并版使用自己的 `$DSH_HOME/dshm-boot-rescue/` |
| `<可见下载目录>/dshm-boot-rescue-backups/backups/` | 合并版新备份写入位置（旧插件移除并冷重启后才允许写） |

旧插件被手动移除后，其既有备份仍会被合并版只读发现；恢复前必须预览并确认。
**不要**手工删除旧备份目录来“清理”，除非用户已经另外保存并确认不再需要。

## 3. 救援（启动失败页）

1. 失败页注入的恢复中心只处理用户明确选择的第三方疑似故障插件。
2. 救援默认**只写一个层**：`<profile>/.dshm-plugin-rows.yml` 的禁用行。
3. 写入成功只表示“已写入”：必须划掉后台重新打开应用（冷重启）；重启前不要新建会话。
4. 冷重启后回到安全中心确认对应 loader 行已 disabled，才表示生效。
5. 若一个写入层无法证明有效：**停止并报告**，不会自动升级到 home patch 或 bundles 层。
6. 回滚只删除本插件精确标记块；回滚可能重新启用故障插件，面板会警告。

## 4. 回滚与失败处理

- 救援写入失败/写后复核失败/外部并发修改：拒绝覆盖并报告，不留下半写状态（tmp + rename）。
- 备份任务失败：保留失败报告；不把失败任务标成成功；不删除既有备份。
- 恢复前预览发现冲突/目标非全新/核心版本不一致：阻止或要求显式确认；恢复后必须冷重启。
- 共存状态无法确认（profile/loader 不可用）：fail closed，备份写入保持只读。
